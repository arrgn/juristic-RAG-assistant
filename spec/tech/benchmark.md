# Бенчмарк RAG и BM25

Протокол контрольной точки по материалам `Занятие_3_RAG_BM25.pdf` (слайды 37–42). Оцениваем поиск по размеченным статьям и отдельно проверяем ответы чата. Реализация описана в [rag.md](rag.md), запуск — в [README.md](../../README.md).

## Набор для контрольной точки

Для воспроизводимого учебного прогона подготовить фиксированный срез из 30 статей Конституции РФ и УК РФ из корпуса проекта. Один документ бенчмарка соответствует одной полной статье. `D01`–`D30` — идентификаторы разметки. Таблица соответствия `document_id → article_id` связывает их с идентификаторами `sources[].id` сервера. Фрагменты одной статьи учитываются как один документ. Зафиксировать `edition_date`, официальный адрес и SHA-256 UTF-8 файла среза.

- `Q01`–`Q10` — вопросы с ответом в срезе. На каждый вопрос разметить все релевантные статьи в срезе, минимум три. Статья релевантна, когда подтверждает хотя бы один конкретный элемент эталона. Указать подтверждающие части статьи и составить краткий эталон с обязательными условиями и исключениями.
- `Q11`–`Q15` — вопросы-ловушки. Эталон — отказ из-за отсутствия сведений в срезе. Для двух и более ловушек подобрать лексическое пересечение с корпусом, чтобы проверить отказ при непустой выдаче. Подтвердить вручную, что ни одна статья среза не даёт запрошенных сведений.
- На каждый вопрос сохранить `id`, `question`, `scope`, `kind` (`answerable` или `trap`), `relevant_document_ids` и `expected_answer`. Для обычных вопросов добавить `evidence` с привязкой частей эталона к документам. Использовать `scope: all` и отдельный пустой `history` для каждого запроса. Зафиксировать разметку до первого прогона.

Папка для будущих материалов — `app/server/data/benchmark/`. `articles.json` использует формат корпуса, описанный в `rag.md`. В `documents.json` хранить отображение ID, в `questions.json` — вопросы с эталонами. В `runs/<run-id>/` хранить параметры `config.json`, результаты по вопросам `results.jsonl` и итог `summary.md`.

### Готовый набор

- [articles.json](../../app/server/data/benchmark/articles.json) — 15 статей Конституции РФ и 15 статей УК РФ.
- [documents.json](../../app/server/data/benchmark/documents.json) — соответствия ID и указатели на места во вложениях.
- [questions.json](../../app/server/data/benchmark/questions.json) — 10 обычных вопросов с эталонами и 5 ловушек.
- [sources.json](../../app/server/data/benchmark/sources.json) — файлы-источники, даты редакций и их SHA-256.

Текст Конституции извлечён из скана публикации № 0001202210060013 с исправлением ошибок OCR. Файл УК — HTML под расширением .doc. Из него извлечены статьи с абзацами и нумерацией, редакционные пометки исключены. Дата редакции УК 15.08.2026 взята из заголовка вложения. Независимая сверка этой редакции с официальным порталом не выполнена.

## Как выполнить прогон

Из корня проекта запустите базовый прогон. Конфигурация по умолчанию использует заглушку и сохраняет полноценные метрики поиска.

```bash
npm --prefix app/server ci
LLM_PROVIDER=stub npm --prefix app/server run benchmark -- bm25-local
```

Для оценивания ответов запустите с настроенным провайдером и новым ID. Пример для локальной OpenAI-совместимой модели:

```bash
LLM_PROVIDER=openai_compatible LLM_BASE_URL=http://localhost:11434/v1 \
  LLM_MODEL='<имя модели>' npm --prefix app/server run benchmark -- llm-local
```

При необходимости задайте `LLM_API_KEY` и `LLM_MODEL_VERSION`. После прогона сопоставьте каждый ответ с эталоном, заполните `review.correct` и `review.reason` в `results.jsonl`, затем посчитайте две метрики качества ответов:

```bash
node app/server/benchmark/score.cjs llm-local
```

1. Загрузить фиксированный срез рабочим загрузчиком корпуса и построить индекс тем же кодом, что использует чат. Зафиксировать SHA коммита, контрольные суммы среза и разметки, правила токенизации и нарезки, `k1`, `b`, `MIN_SCORE`, `MAX_CONTEXT_DOCS`, провайдер, имя и версию модели, версию промпта и параметры генерации.
2. Для всех 15 вопросов собрать ранжированные ID и баллы из `SearchService` после группировки фрагментов и применения `MIN_SCORE`. Для сравнения поиска фиксировать `k = 3`. Для ответа чата оставить рабочий `MAX_CONTEXT_DOCS` (по умолчанию 5) и записать его в отчёте.
3. Отправить все вопросы в `POST /api/chat`, передавая `message`, `scope` и пустой `history`. Сохранить `answer`, `sources` и признак технической деградации. Для каждого вопроса записать первые три ID поиска, баллы и порядок, фактические ID переданного контекста, HTTP-статус и ручную оценку с причиной.
4. Сравнить ответы с эталонами. Для ответа по существу проверить полноту, отсутствие добавленных утверждений и подтверждение источником. Для отказа проверить явное сообщение о недостатке сведений и отсутствие домыслов. Таймаут, сбой сервера и фраза о недоступности LLM учитываются как ошибочные ответы; их количество вывести отдельно. Заглушка LLM подходит для проверок пайплайна. Метрики качества ответов требуют рабочего провайдера.
5. При сравнении менять один параметр за раз и сохранять один срез, вопросы, эталоны и `k`. Подбор `MIN_SCORE` и других параметров выполнять на отдельных вопросах разработки. Контрольные вопросы использовать для итоговой оценки.

## Метрики и отчёт

`R(q)` — множество релевантных ID из разметки, `Top3(q)` — первые три уникальных ID статей по данным поиска. Если найдено меньше трёх статей, считать по фактической выдаче. Ранг начинается с единицы.

| Метрика | Расчёт |
| --- | --- |
| `Recall@3` | Среднее по 10 обычным вопросам от `size(Top3(q) ∩ R(q)) / size(R(q))` |
| `MRR@3` | Среднее по тем же 10 вопросам от `1 / rank`, где `rank` — позиция первой релевантной статьи в первых трёх. При её отсутствии вклад равен 0 |
| `Accuracy` | Полностью правильные ответы с подтверждением в контексте / 10 |
| `Correct Rejection Rate` | Корректные отказы на вопросах-ловушках / 5 |

Проверка расчёта на примере занятия. Для эталона `{A, D, F}` при выдаче `[B, A, D]` получаем `Recall@3 = 2/3`, `RR@3 = 1/2`.

После прогона приложить четыре измеренных значения и разбор ошибок по вопросам. Для каждого сбоя указать, где потерялись сведения: статья отсутствует в срезе, поиск её пропустил, фрагмент не вошёл в контекст, модель неверно использовала контекст или провайдер вернул ошибку.
