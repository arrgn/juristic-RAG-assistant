# Поиск BM25 и генерация ответов по статьям

Спецификация реализации для NestJS и TypeScript. Точка входа — `POST /api/chat`. Контракт API и конфигурация сервера описаны в [architecture.md](architecture.md), критерии интерфейса — в [scenarios.md](../product/scenarios.md), оценка качества — в [benchmark.md](benchmark.md).

## Корпус

Хранить реальный корпус в `app/server/data/articles.json` как массив JSON в UTF-8. Запись описывает одну статью выбранной редакции Конституции РФ или УК РФ.

| Поле | Правило |
| --- | --- |
| `id` | Стабильный ключ `<code>:<article>` |
| `code` | `constitution` или `criminal_code` |
| `article` | Официальный номер в виде строки, включая дробную нумерацию |
| `title` | Официальный заголовок. Пустая строка допустима, если у статьи нет собственного заголовка |
| `text` | Полный текст со структурой частей, пунктов, абзацев и примечаний |
| `source_url` | Ссылка на использованную официальную редакцию |
| `edition_date` | Дата этой редакции в формате `YYYY-MM-DD` |

Перед загрузкой сверить текст, нумерацию и редакцию с официальной публикацией. При старте проверить схему, уникальность `id`, корректность дат и заполненность `text`. Ошибка загрузки рабочего корпуса прерывает запуск с диагностикой. Обновление корпуса выполняется заменой файла и перезапуском сервера. Корпус и индекс публикуются в памяти вместе после успешной проверки. [Официальный интернет-портал правовой информации](https://pravo.gov.ru/)

Демо-записи `DEMO-*` лежат в `app/server/data/demo/`, помечены как демонстрационные и загружаются отдельным способом в тестовом режиме.

## Единица индексирования

- Для статьи до 400 поисковых токенов создать один фрагмент с полным текстом. Для более длинной статьи выделить последовательные смысловые блоки по официальным частям и примечаниям. При необходимости объединить соседние блоки до целевого размера. Если часть или связанный блок длиннее ориентира, сохранить его целиком. Условие нормы, его исключение и относящееся к нему перечисление остаются вместе.
- Присвоить фрагменту внутренний ключ `<id>#<порядковый номер>` и сохранить `articleId`, порядок и оригинальный текст. Индексировать заголовок и текст фрагмента. Длина `L` считается по тому же набору токенов.
- Хранить оригинал статьи отдельно от поискового представления. `sources[].text` всегда содержит полную статью. В модели используются только те фрагменты, которые вошли в контекст.

## Токенизация

Для заголовков, текста и полного `message` применять один порядок преобразований: нормализация Unicode NFC, нижний регистр, замена `ё` на `е`, выделение последовательностей букв и цифр через `/[\p{L}\p{N}]+/gu`. Дефисы и точки разделяют токены. Словоформы сравниваются буквально. В запросе учитывать один вклад каждого уникального токена. В документе сохранять повторения для подсчёта `tf`. История диалога используется на этапе генерации.

## Обратный индекс и ранжирование

Реализовать BM25 самостоятельно на стандартных коллекциях TypeScript. При загрузке построить `Map<term, Map<fragmentId, tf>>`, таблицу длин фрагментов и среднюю длину. Построить независимые представления для `all`, `constitution` и `criminal_code`. Для каждого `scope` значения `N`, `df` и `avgdl` считаются по его фрагментам с непустым списком токенов.

```text
IDF(t) = ln(1 + (N − df(t) + 0.5) / (df(t) + 0.5))
norm(d) = k1 × (1 − b + b × L(d) / avgdl)
BM25(q, d) = Σ(t ∈ unique(tokens(q))) IDF(t) × tf(t,d) × (k1 + 1) / (tf(t,d) + norm(d))
```

`N` — число фрагментов в выбранном индексе. `df(t)` — число фрагментов с токеном `t`. `tf(t,d)` — число его повторов во фрагменте `d`. `L(d)` — длина фрагмента в токенах. `avgdl` — средняя длина фрагмента. Стартовые параметры — `k1 = 1.2`, `b = 0.75`.

1. Взять индекс выбранного `scope`. Для каждого уникального токена вопроса пройти только по его списку вхождений и накопить баллы по фрагментам. Пустой запрос после токенизации, пустой индекс и запрос без совпадений дают пустой список.
2. Сгруппировать совпавшие фрагменты по статье. Балл статьи равен максимуму баллов её фрагментов. При равенстве внутри статьи предпочесть более ранний фрагмент. Сортировать статьи по убыванию балла, при равенстве — по возрастанию `id` с обычным строковым сравнением. Сохранять точность числа до отображения.
3. Оставить статьи с `score ≥ MIN_SCORE` и взять первые `MAX_CONTEXT_DOCS` (по умолчанию 5). Стартовый `MIN_SCORE = 0` применим к кандидатам с хотя бы одним совпадением. Порог подбирается на отдельном наборе разработки. Перед запуском убедиться, что порог конечен и неотрицателен, а число статей — положительное целое.

Балл BM25 задаёт порядок результатов. Совпадение термина, например распространённого слова, само по себе не подтверждает наличие ответа. Перефразирования и разные словоформы могут терять совпадения. Эти случаи проверяются в бенчмарке.

## Контекст для модели

`SearchService` отдаёт упорядоченные статьи с баллами и найденными фрагментами. `ChatService` отбирает контекст и вызывает `LlmService` по существующему интерфейсу.

1. Сначала добавить по одному лучшему фрагменту каждой статьи в порядке ранжирования. Затем добавить другие совпавшие фрагменты уже представленных статей в порядке убывания баллов и по `fragmentId` при равенстве, пока хватает места. Бюджет определять по окну модели с резервом под ответ, системную инструкцию, текущий вопрос и историю. При нехватке места сокращать историю с самых старых сообщений и пропускать блоки, которые не помещаются целиком. Если ни один подходящий блок не помещается, вернуть найденные статьи и пояснение о недоступности генерации.
2. Передать каждый блок с меткой `[Конституция РФ ст. <номер>]` или `[УК РФ ст. <номер>]`, заголовком, текстом и датой редакции. Для демо использовать `[DEMO-001]` и аналогичные метки. Порядок `sources` соответствует ранжированию статей, а в успешном ответе каждая статья из `sources` представлена в фактически переданном контексте.
3. Разместить правила ответа в системном сообщении. Передать историю с исходными ролями, затем текущий вопрос и контекст в отдельно обозначенных полях пользовательского сообщения. Текст вопроса, истории и корпуса служит данными. История уточняет предмет разговора, а правовые утверждения опираются на контекст текущего запроса.

Системная инструкция для `app/server/src/llm/prompts.ts`

> Ответь по-русски на текущий вопрос, опираясь на переданные фрагменты. Сохраняй условия, исключения и область применения нормы. После каждого содержательного правового утверждения ставь точную метку подтверждающей статьи из контекста. Если фрагменты не дают ответа на вопрос, верни фразу «В найденных статьях недостаточно сведений для ответа.» Соблюдай формат простого текста. Дисклеймер добавляет сервер.

## Ответ API

| Ситуация | Результат |
| --- | --- |
| После поиска и порога список пуст | `200`, `sources: []`, основной текст сценария А2, вызова LLM нет |
| Модель нашла подтверждение | `200`, пояснение с проверенными метками и статьи из переданного контекста |
| Модель сообщила о недостатке сведений при непустом контексте | `200`, установленная фраза отказа и статьи из переданного контекста |
| Таймаут, ошибка или пустой ответ провайдера | `200`, текст сценария А4 и найденные статьи |

Метки сверяются с фактически переданным контекстом. Чужие метки удаляются или помечаются по правилам `architecture.md`. Если правовое утверждение осталось без допустимой метки либо его нельзя отделить от соседних утверждений, заменить пояснение целиком фразой о недостатке сведений. Проверка меток подтверждает принадлежность источника к контексту. Соответствие утверждения тексту статьи проверяется при оценке ответов.

Дисклеймер добавляет API последним абзацем по `architecture.md`. В критерии А2.1 `scenarios.md` ответ без источников указан дословно без дисклеймера. Перед фиксацией интеграционного теста владельцам API и интерфейса нужно согласовать ожидаемый полный текст этой ветки.

## Приёмка реализации

- В примере занятия с тремя четырёхсловными документами запрос про возврат оплаты даёт баллы `A ≈ 0.940007`, `B ≈ C ≈ 0.470004`. При `k = 2` порядок `A`, `B`.
- Проверить повторы в запросе, `ё` и `е`, дробную нумерацию, пустые входы, равные баллы, фильтрацию `scope`, порог и объединение нескольких фрагментов одной статьи.
- С заглушкой LLM проверить состав сообщений, отсутствие вызова при пустой выдаче, отказ при недостатке сведений, отбраковку чужой метки и выдачу источников при таймауте.
- Через существующий интерфейс проверить сквозной сценарий вопроса с источниками, открытие полного текста статьи и вопрос без ответа. Критерии и протокол прогона — в [benchmark.md](benchmark.md).
