# Юридический RAG-ассистент — архитектура

> **Статус: Этап 1 (2026-10-10).** Документ фиксирует решения до написания кода. Владелец — Ушаков Леонид (интеграция, бэкенд); поиск по корпусу описывает Грачев Константин в `spec/tech/rag.md` (создаётся), интерфейс — Корегин Илья в [spec/product/scenarios.md](../product/scenarios.md). Правила изменения — [AGENTS.md](../../AGENTS.md).

## 1. Состав системы

Три контейнера в одной сети Docker Compose:

| Сервис | Папка | Роль | Порт наружу |
|---|---|---|---|
| `nginx` | `app/nginx/` | единственная точка входа: отдаёт собранную статику клиента, проксирует `/api/*` на `server` | 80 (настраивается в `.env`) |
| `client` | `app/client/` | React + TypeScript (Vite); при сборке образа собирается в статику, которую забирает `nginx` | нет |
| `server` | `app/server/` | NestJS + TypeScript: API, корпус, поиск, обращение к LLM | нет (только внутри сети) |

Клиент и сервер видны браузеру как один адрес: запросы к `/api/*` идут через Nginx, поэтому CORS не нужен. В разработке клиент можно запускать отдельно (`vite dev`) с прокси `/api` на сервер.

```text
Браузер ──► nginx:80 ──► /        статика клиента
                  └────► /api/*   ──► server:3000
                                       │
                          ┌────────────┼─────────────┐
                          ▼            ▼             ▼
                     ChatService → SearchService → LlmService ──► провайдер LLM
                                       │
                                  корпус статей
```

## 2. Пайплайн обработки вопроса

`POST /api/chat` выполняет по порядку:

1. **Проверка входа** (DTO + `class-validator`): длина, число слов, `scope`, `history`.
2. **Поиск** (`SearchService`): по `message` (с учётом `scope`) выбираются до `MAX_CONTEXT_DOCS` статей с `score ≥ MIN_SCORE`. Алгоритм и параметры — `spec/tech/rag.md`.
3. **Нет статей** → ответ с готовым текстом «Ничего не найдено» (раздел 5 в [scenarios.md](../product/scenarios.md)), `sources = []`; LLM не вызывается.
4. **Генерация** (`LlmService`): модели передаются системный промпт, статьи как контекст, последние сообщения `history` и вопрос. Модель обязана ссылаться только на переданные статьи.
5. **Проверка ссылок:** метки статей в ответе сверяются с `sources`; метка без статьи в источниках заменяется нейтральным текстом или помечается как отсутствующая.
6. **Дисклеймер** «Это справочная информация, а не юридическая консультация.» добавляет сервер последним абзацем.
7. **Недоступность LLM** (таймаут, сеть, ошибка провайдера) → ответ 200 с текстом «Пояснение недоступно: языковая модель не ответила. Список подходящих статей ниже.», дисклеймером и непустым `sources`.

## 3. Структура `app/server/`

```text
app/server/
├── Dockerfile
├── package.json
├── data/                     # корпус статей (реальный) и демо-записи
├── src/
│   ├── main.ts               # префикс /api, валидация, запуск
│   ├── app.module.ts
│   ├── health/               # GET /api/health
│   ├── chat/                 # контроллер, DTO, ChatService (оркестрация пайплайна)
│   ├── corpus/               # загрузка и хранение статей
│   ├── search/               # предобработка, индекс, ранжирование
│   └── llm/                  # LlmService, провайдеры, промпт
└── test/
```

Модули связаны через внедрение зависимостей Nest: `ChatService` знает только интерфейсы `SearchService` и `LlmService`. Это позволяет подменять поиск и модель заглушками в тестах и менять сам фреймворк сервера, не трогая контракт.

## 4. Корпус

Статьи Конституции РФ и Уголовного кодекса РФ хранятся файлом в `app/server/data/` и загружаются в память при старте. Запись:

| Поле | Тип | Содержимое |
|---|---|---|
| `id` | строка | идентификатор статьи в корпусе |
| `code` | строка | `constitution` или `criminal_code` |
| `article` | строка | номер статьи как в официальной редакции |
| `title` | строка | заголовок статьи |
| `text` | строка | полный текст статьи |
| `source_url` | строка | адрес официальной редакции |
| `edition_date` | строка | дата редакции (ГГГГ-ММ-ДД) |

Тексты берутся только из официальных редакций, выдуманные нормы запрещены (AGENTS.md, раздел 2). Демо-записи `DEMO-001`, `DEMO-002`, `DEMO-003` лежат отдельно (`data/demo/`) и в реальный корпус не попадают. Формат хранения, нарезка длинных статей на фрагменты и выбор поиска (лексический, векторный или гибридный) фиксирует `spec/tech/rag.md`.

## 5. Контракт API

Префикс всех маршрутов — `/api`. Любое изменение — по протоколу AGENTS.md, раздел 4.

### `POST /api/chat`

| Поле запроса | Тип | Правило |
|---|---|---|
| `message` | строка | после обрезки пробелов по краям: 3–1000 символов, не меньше 3 слов; слово — непрерывная последовательность букв или цифр (`[^\W_]+` в Python-нотации, `/[\p{L}\p{N}]+/gu` в JS) |
| `scope` | строка | `all` (по умолчанию), `constitution`, `criminal_code` |
| `history` | массив | до 10 объектов `{ "role": "user" \| "assistant", "content": строка }`, `content` не длиннее 4000 символов |

| Поле ответа | Тип | Содержимое |
|---|---|---|
| `answer` | строка | простой текст без Markdown, абзацы разделены `\n\n`; ссылки на статьи — метки в квадратных скобках; последний абзац — дисклеймер |
| `sources` | массив | использованные статьи по убыванию `score`, при равенстве — по `id` |
| `sources[].id` | строка | идентификатор статьи в корпусе; у демо-записей `DEMO-001` и т. д. |
| `sources[].code` | строка | `constitution` или `criminal_code` |
| `sources[].article` | строка | номер статьи |
| `sources[].title` | строка | заголовок статьи |
| `sources[].text` | строка | полный текст статьи |
| `sources[].source_url` | строка | адрес официальной редакции |
| `sources[].score` | число | оценка релевантности, неотрицательная |

Пример ответа (демонстрационные данные):

```json
{
  "answer": "Демонстрационные данные: ответ составлен по вымышленным записям.\n\n[DEMO-001] Вымышленная статья описывает защиту тайны переписки.\n\nЭто справочная информация, а не юридическая консультация.",
  "sources": [
    {
      "id": "DEMO-001",
      "code": "constitution",
      "article": "DEMO",
      "title": "Тайна переписки (демонстрационная запись)",
      "text": "Демонстрационный текст, не являющийся нормой права.",
      "source_url": "демонстрационные данные",
      "score": 12.47
    }
  ]
}
```

Коды ответов: 200 — успех (в том числе пустой `sources` и недоступная модель); 422 — не прошла проверка полей; 5xx — ошибка сервера. Тело 422 — стандартное для NestJS (`message`, `error`, `statusCode`); интерфейс его не показывает.

### `GET /api/health`

Ответ 200: `{ "status": "ok", "version": "<версия>", "llm": "<провайдер>" }`.

## 6. Выбор LLM и переключатель провайдера

Решение о конкретной модели и провайдере пока не принято; его принимают Ушаков и Грачев и записывают здесь. Архитектура не привязана к решению: `LlmService` работает через интерфейс `LlmProvider` с одним методом «сообщения → текст», провайдер выбирается переменной `LLM_PROVIDER`:

| Значение | Что делает |
|---|---|
| `stub` | возвращает заготовленный текст без сети; для тестов и прототипа |
| `openai_compatible` | любой сервер с OpenAI-совместимым API (локальный Ollama, LM Studio, vLLM либо внешний сервис) |

Критерии выбора: качество русского языка и юридических формулировок, возможность работать локально (вопросы пользователей не уходят во внешний сервис), задержка ответа, требования к железу.

## 7. Переменные окружения

Задаются в `app/.env`, образец — `app/.env.example`. Новая переменная добавляется в образец и в эту таблицу в одном коммите.

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `NGINX_PORT` | порт Nginx на хосте | `80` |
| `SERVER_PORT` | порт сервера внутри сети | `3000` |
| `LLM_PROVIDER` | `stub` или `openai_compatible` | `stub` |
| `LLM_BASE_URL` | адрес API провайдера | — |
| `LLM_MODEL` | имя модели | — |
| `LLM_API_KEY` | ключ провайдера; только на сервере, не `VITE_*` | — |
| `LLM_TIMEOUT_MS` | таймаут вызова модели | `30000` |
| `MAX_CONTEXT_DOCS` | сколько статей передавать модели | `5` |
| `MIN_SCORE` | порог релевантности; подбирается на проверочных вопросах | определяется в `rag.md` |

## 8. Docker и Nginx

- `app/docker-compose.yml` описывает сервисы `nginx`, `client`, `server`; `server` читает `.env`, `nginx` зависит от `server`.
- Образы собираются многоступенчато: клиент — `node` для сборки Vite, результат копируется в образ `nginx`; сервер — `node` для сборки и лёгкий образ для запуска.
- `app/nginx/nginx.conf`: `location /` — статика с `try_files … /index.html` (клиент без маршрутизации по путям, но запас на будущее); `location /api/` — `proxy_pass` на `server:3000`; таймаут чтения не меньше `LLM_TIMEOUT_MS` плюс запас.
- Секреты в образы не вшиваются, передаются переменными окружения при запуске (AGENTS.md, раздел 6).

## 9. Логирование и данные пользователей

- Сервер хранит диалоги только в памяти запроса: история приходит от клиента в `history`, на сервере нигде не сохраняется.
- В логи пишутся метаданные (время, код ответа, длительность, число найденных статей), но не текст вопросов и ответов.
- Выбранный провайдер LLM получает вопрос и найденные статьи; при внешнем провайдере это нужно показать пользователю в документации запуска.
