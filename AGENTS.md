# AGENTS.md — правила работы с репозиторием

Правила обязательны для ИИ-агентов (Claude Code и других, которые читают `AGENTS.md`) и для участников команды. Claude Code читает `CLAUDE.md`, а тот подключает этот файл строкой `@AGENTS.md`; правила хранятся только здесь. Агент работает от имени участника, который его запустил, и только в его зоне (раздел 3). Если правило мешает задаче, его не обходят, а сообщают об этом владельцу зоны.

## 1. Порядок любого изменения

1. **Прочитать документацию** по таблице ниже — до изменения кода. Если код и документ расходятся, выяснить у владельца, что из них верно; не выбирать молча.
2. **Изменить код** в своей зоне.
3. **Обновить документацию в том же коммите**, если изменилось описанное в ней: поведение, формат данных, контракт API, тексты интерфейса, стек. Рефакторинг без изменения поведения документацию не меняет.
4. **Запустить проверки** (раздел 5).
5. **Обновить `CHANGE_HISTORY.md`**: новая запись сверху, дата `ГГГГ-ММ-ДД`, кто и что сделал.
6. **Пройти чек-лист** «Готово к коммиту» (раздел 9).

| Область изменения | Прочитать до изменения | Обновить в том же коммите |
|---|---|---|
| Интерфейс — `app/client/` | `spec/product/scenarios.md`; контракт API в `spec/tech/architecture.md` | `spec/product/scenarios.md`: экраны, сценарии, строки интерфейса |
| API, чат-пайплайн, модуль LLM — `app/server/src/chat/`, `health/`, `llm/` | `spec/tech/architecture.md`, `spec/product/scenarios.md` | `spec/tech/architecture.md` (контракт — по протоколу раздела 4) |
| Корпус и поиск — `app/server/src/corpus/`, `search/`, `app/server/data/` | `spec/tech/rag.md`, `spec/tech/architecture.md` (раздел «Корпус») | `spec/tech/rag.md` |
| Промпт LLM — `app/server/src/llm/prompts.ts` | `spec/tech/rag.md`; формат `answer` в `spec/tech/architecture.md` | документ, где описано изменённое правило |
| Nginx, Dockerfile, `docker-compose.yml`, `.env.example` | `spec/tech/architecture.md` (разделы «Docker и Nginx», «Переменные окружения»), `README.md` | `spec/tech/architecture.md`, `README.md`: структура и раздел «Запуск» |
| Тесты | `spec/tech/architecture.md`: контракт API | не требуется: тесты следуют за документацией |
| Назначение, пользователи, границы продукта | `README.md`, `spec/product/scenarios.md` | `README.md`, `spec/product/scenarios.md` |
| Стек и зависимости | `README.md`, `spec/tech/architecture.md` | `README.md`, `spec/tech/architecture.md`, `CHANGE_HISTORY.md` |

Документ `spec/tech/rag.md` (корпус, предобработка, поиск, проверочные вопросы, метрики) создаёт Грачев Константин, когда начнёт реализацию поиска. До этого поиск описан в `spec/tech/architecture.md` только как интерфейс.

## 2. Жёсткие ограничения

Нарушать нельзя, в том числе «временно» или «для проверки».

1. **Не выдумывать нормы права.** Номера статей, части, пункты и тексты берутся только из официальных редакций Конституции РФ и Уголовного кодекса РФ (официальный интернет-портал правовой информации, `publication.pravo.gov.ru`, либо иной официальный источник). Корпус хранит дату и источник редакции.
2. **Ответ строится только на найденных статьях.** Модель получает статьи из корпуса как контекст и не должна ссылаться на статьи, которых в контексте нет. Сервер проверяет ссылки `[…]` в ответе: статья, которой нет среди источников, помечается как отсутствующая или удаляется.
3. **Дисклеймер добавляет API, а не модель:** «Это справочная информация, а не юридическая консультация.» Он есть в каждом ответе и в подвале интерфейса.
4. **Демонстрационные данные** (моки для прототипа и тестов) имеют id вида `DEMO-001`, пометку «демонстрационные данные» и вымышленный текст. Никаких реальных номеров статей в моках «для примера»; формат ссылки описывается только шаблоном `ст. <номер>`. Демо-записи не смешиваются с реальным корпусом.
5. **Стек:** клиент — React + TypeScript; сервер — NestJS + TypeScript; Nginx; всё запускается через Docker Compose. Замена любого слоя (в том числе сервера) — только по согласованию всей команды и с записью в `CHANGE_HISTORY.md` и `README.md`.
6. **Размещение:** весь код и Docker-файлы — в `app/` (`app/client`, `app/server`, `app/nginx`). В корне репозитория лежат только документы и `LICENSE`.
7. **Секреты не в git** (раздел 6).

Связанные правила проекта:

- Вопросы пользователей — персональные данные в широком смысле: не логировать текст вопросов целиком вместе с идентификаторами пользователя и не передавать их сторонним сервисам, кроме выбранного провайдера LLM. Выбор провайдера (локальный или внешний API) фиксируется в документации архитектуры.
- Новые зависимости — только по согласованию: сервер — с Ушаковым, клиент — с Корегиным.

## 3. Зоны ответственности

| Участник | Роль | Зона |
|---|---|---|
| Грачев Константин | BM25 и RAG | `app/server/src/corpus/`, `app/server/src/search/`, `app/server/data/`, `app/server/src/llm/prompts.ts`, `spec/tech/rag.md`, проверочные вопросы и тетрадки оценки качества поиска |
| Ушаков Леонид | Интеграция (бэкенд) | остальной `app/server/` (`chat/`, `health/`, `llm/` кроме `prompts.ts`, `main.ts`, тесты), `app/nginx/`, Dockerfile, `app/docker-compose.yml`, `app/.env.example`, `spec/tech/architecture.md`, общие файлы в корне (`README.md`, `AGENTS.md`, `CLAUDE.md`, `CHANGE_HISTORY.md`, `.gitignore`) |
| Корегин Илья | Продукт и интерфейс | `app/client/` (включая его Dockerfile), `spec/product/` |

- Каждый работает в своей зоне. Изменение в чужой зоне — только по согласованию с владельцем: предложить правку (сообщение в чате команды, issue или pull request), владелец принимает её или вносит сам.
- Тесты своего модуля (например, поиска) добавляются в `app/server/test/` по согласованию с Ушаковым.
- ИИ-агент меняет файлы только в зоне участника, который его запустил. Если задача требует правки в чужой зоне, агент останавливается и описывает нужное изменение, а не вносит его.
- `CHANGE_HISTORY.md` — общий журнал: каждый добавляет свои записи и не правит чужие.
- `AGENTS.md` меняется по согласованию всей команды.
- В `README.md` раздел «Запуск» стоит между маркерами `<!-- run:start -->` и `<!-- run:end -->`; маркеры не удалять.

## 4. Изменение контракта API

Контракт — запросы и ответы эндпоинтов сервера (`GET /api/health` и `POST /api/chat`), описанные в `spec/tech/architecture.md`,: поля, типы, правила проверки, формат `answer` и ссылок на статьи. На него опираются сервер, клиент, моки и тесты. Порядок изменения:

1. Согласовать изменение с Ушаковым (владелец контракта) и Корегиным (клиент); если затронуты поиск или формат `answer` — и с Грачевым.
2. Сначала документ с контрактом (`spec/tech/architecture.md`): таблицы запроса и ответа, правила проверки, JSON-пример.
3. Сервер: DTO и контроллеры в `app/server/`.
4. Клиент: типы и функция вызова API в `app/client/`, мок.
5. Тесты сервера и сборка клиента проходят; в `CHANGE_HISTORY.md` — запись «изменён контракт API: что было → что стало».

Шаги 2–4 выполняются согласованно: одним коммитом или подряд в оговорённом порядке, без других изменений между ними. Менять контракт «по пути» — только в коде, только в моке или только в тестах — нельзя.

## 5. Проверки

Конкретные команды фиксируются здесь, когда появится код. Ожидаемый набор:

```bash
cd app/server && npm run lint && npm test
cd app/client && npm run lint && npm run build
cd app && docker compose build
```

- Тесты не требуют сети и настоящей LLM: модель в тестах заменяется заглушкой (stub-провайдером) или моком HTTP.
- Когда появится поиск по статьям, добавляется набор проверочных вопросов с заранее известными релевантными статьями и метрики качества поиска (например, Recall@5 и MRR). Изменения в корпусе, предобработке, поиске и промпте не должны ухудшать метрики без объяснения; значения до и после записываются в `CHANGE_HISTORY.md`.
- Если тест падает, сначала выяснить, что неверно — код или документация. Ожидаемые значения в тестах под код не подгоняются.

## 6. Секреты и `.env`

- `.env` не коммитится (он в `.gitignore`). Настройки (провайдер и модель LLM, ключи, порты) задаются в `app/.env`; образец без секретов — `app/.env.example`. Новая переменная окружения добавляется в `.env.example` и в документацию в том же коммите.
- Ключи, токены и пароли не записываются в код, тесты, документы, Dockerfile и сообщения коммитов. Секреты передаются в контейнеры через переменные окружения, а не вшиваются в образ.
- Всё, что начинается с `VITE_`, попадает в код страницы и видно в браузере, поэтому секреты в такие переменные не записывают. Ключ LLM живёт только на сервере.
- Если секрет попал в коммит, сообщить команде и заменить (отозвать) ключ: удаление файла следующим коммитом не помогает — файл остаётся в истории git.

## 7. Корпус и демонстрационные данные

- Реальный корпус: статьи Конституции РФ и Уголовного кодекса РФ с полями «источник права», номер статьи, заголовок, текст, дата и адрес официальной редакции. Хранится в `app/server/data/` (формат — в `spec/tech/architecture.md`, раздел «Корпус», детали — в `spec/tech/rag.md`) и не смешивается с демо-данными.
- Демо-записи: id `DEMO-001`, `DEMO-002`, …, поле `source` — «демонстрационные данные». Тексты придуманы и не описывают реальные нормы.
- Пометка обязательна везде, где демо-записи видит пользователь: в интерфейсе — плашка «Демонстрационные данные…» (по префиксу `DEMO-` в id), в ответе API — вводная фраза `answer`.
- Демо-записи, их копии в моке клиента, заглушке сервера и в тестах меняются согласованно.

## 8. Дополнительно для ИИ-агентов

- Не выполнять `git commit`, `git push` и операции, переписывающие историю (`git rebase`, `git reset --hard`, `git push --force`), без явной просьбы человека.
- Не реализовывать то, что на текущем этапе намеренно оставлено заготовкой, если об этом прямо не попросили.
- Не выдумывать статьи, их тексты, номера, метрики и результаты проверок. Цифры качества берутся только из реального прогона.
- Документы, комментарии и докстринги — на русском; имена в коде — на английском. Ссылки на файлы — относительные пути от корня репозитория.
- В конце работы сообщить человеку: что изменено, какие проверки запущены и с каким результатом, что не проверено и почему.

## 9. Чек-лист «Готово к коммиту»

- [ ] Изменения — в своей зоне или согласованы с владельцем (раздел 3).
- [ ] Нужная документация прочитана и обновлена в этом же коммите.
- [ ] Жёсткие ограничения (раздел 2) не нарушены: нет выдуманных статей, ответ опирается только на найденные источники, код лежит в `app/`.
- [ ] Контракт API не изменён или изменён по протоколу (раздел 4).
- [ ] Проверки раздела 5 проходят.
- [ ] В `CHANGE_HISTORY.md` добавлена запись.
- [ ] В `git status` нет `.env`, секретов, `node_modules/`, `dist/`, логов.
- [ ] Сообщение коммита — `тип(область): что сделано` по-русски, область можно опустить (`chore: …`); типы `feat`, `fix`, `docs`, `test`, `refactor`, `chore`. Пример: `docs(scenarios): сценарии чата и строки интерфейса`.
